# Capability: ACP stdio lifecycle and gateway-backed prompt turns (`tachyon-acp`)

Capability documentation required by `AGENTS.md` § New capability checklist. Covers the `tachyon-acp` surface added by acp-adapter-lifecycle tickets 01–03 — the ND-JSON-RPC stdio loop, the `initialize` handshake, the gateway liveness probe, `session/new`, the full `session/prompt` turn pipeline, and `session/cancel` (drain-acknowledged, both wire forms) with the stream-edge handling (`ResyncRequired` re-subscribe, approval-park refusal) (ADR-0005's first adapter slices). Glossary term: **ACP adapter** (CONTEXT.md) — a gateway client, never an execution path. `session/load` ships with this revision (replay + recorded-turn gate, below). Still-not-shipped slices of issue #57: MCP-at-setup; that capability is not described here because it is not shipped yet, and nothing here advertises it.

## Why deterministic code cannot already solve it

The peer is an untrusted external editor process speaking its own protocol over a pipe Tachyon does not control: no deterministic code inside Tachyon can make that peer speak gateway frames, and no model should decide what the adapter claims to support. What must be deterministic is everything on this side of the pipe — framing, id correlation, version negotiation, param validation, the sequential-turn guard, the idempotency-key registry, journal→chunk mapping, and the `stopReason` verdict — and above all the advertise-only-implemented rule (ADR-0005:31): a capability object that drifts one field ahead of the code is a client-visible lie. The adapter therefore hard-codes the advertisement from the implemented set, gates every request on a fail-closed liveness probe, validates params before any gateway contact, and runs no model/Jev call of any kind (the gateway's Task Supervisor runs every turn; the adapter only frames it).

## Input / output schema

- **Input:** UTF-8 newline-delimited JSON-RPC 2.0 on stdin, one object per line. Requests: `{ "jsonrpc": "2.0", "id": string|number, "method": string, "params"?: ... }`. Notifications (no id, e.g. `notifications/initialized`) are consumed without reply. `initialize` params must be an object carrying an integer `protocolVersion`, else typed `-32602` ("Invalid params: initialize requires an integer protocolVersion"). The adapter answers a client that requests any version with `protocolVersion: 1` — ACP negotiation: the agent replies with the latest version it speaks (ADR-0005:21).
- **Output:** stdout carries only valid ACP frames (one compact JSON object per line, flushed per frame); logs go to stderr (tracing, `RUST_LOG`-overridable, default `info`). Frame shapes:
  - `initialize` success: `result = { "protocolVersion": 1, "agentCapabilities": { "loadSession": true, "promptCapabilities": { "image": false, "audio": false, "embeddedContext": false } }, "agentInfo": { "name": "tachyon-acp", "title": "Tachyon ACP adapter", "version": <crate version> }, "authMethods": [] }` — byte-exactly pinned by the golden test; no `mcpCapabilities`, no `sessionCapabilities`, no `fs`/`terminal` claims, nothing unimplemented (ADR-0005:27-31).
  - `session/new` success: `result = { "sessionId": <gateway session_id> }` — identity mapping: the ACP `sessionId` IS the durable Tachyon `SessionId`, byte-for-byte, with no alias store (proved by echoing it through `GetSession`). `params = { "cwd": <absolute path>, "mcpServers"? }`.
  - `session/prompt` success: `result = { "stopReason": "end_turn" | "cancelled" | "refusal", "content": [ { "type": "text", "text": <final agent message from the task's conversation tail> } ] }` — `stopReason` derives from terminal `TaskStatus` (`Completed → end_turn`, `Cancelled → cancelled`) plus ONE adapter-side default: a gateway `Deny` whose bounded 5 s settle grace elapses with no terminal status answers `refusal` with empty `content` (the gateway journals no terminal status after a deny — pre-existing gap, logged as a known issue); that verdict is never `turn_timed_out` and never a guessed `end_turn`; `Failed` has no schema-legal stopReason (the pinned ACP `schema-v1.23.0` `StopReason` enum is `end_turn|max_tokens|max_turn_requests|refusal|cancelled` — no `"error"` member), so it answers a typed `-32004` `data: "task_failed"` ERROR frame instead of a success frame, and any other status is typed `-32004` `data: "ambiguous_task_status"` — never a guessed verdict. `TaskStatus::Failed` is not currently constructed by production code; the branch is pinned by unit test and will matter when core starts setting it. The success response shape is byte-pinned by golden tests.
  - `session/update` (agent-initiated notification, no id, streamed while a prompt runs): `{ "jsonrpc": "2.0", "method": "session/update", "params": { "sessionId": <id>, "update": { "sessionUpdate": "agent_message_chunk", "content": { "type": "text", "text": <chunk> } } } }` — only journalled `agent_message` events map to chunks; every other journal kind (`stage`, `status`, `evidence_summary`, `changed_files`, `verification_*`, …) is omitted, never mislabeled.
  - `session/cancel` (both wire forms): ACP models it as a client NOTIFICATION (schema `CancelNotification`, `{ "sessionId": <id> }`), which the adapter runs through the same pipeline but NEVER answers with a frame; an id-bearing request form gets `result = {}` (byte-pinned), and both forms await the gateway's `CancelTask` response — the Supervisor's drain acknowledgement (ADR-0005:49) — before anything else is read or written, which pins the frame order: drain ack → cancel reply → the resolved prompt's `stopReason: "cancelled"`. No active turn ⇒ the same idempotent `result: {}` after a `GetSession` existence check (no `CancelTask` is ever issued; the reply is byte-identical to the active-turn case). Unknown session ⇒ `-32002` `data: "unknown_session"`; a task that was already terminal ⇒ the same idempotent ok (gateway `illegal_transition` tolerated). A whole cancel that does not settle within 120 s ⇒ `-32004` `data: "cancel_timed_out"` (the reply never claims a drain that was not observed).
  - `session/load` success: `result = {}` (schema `LoadSessionResponse`, no optional fields supported) AFTER streaming the whole recorded conversation as `session/update` notifications — every `turn_seq`-ordered turn's `{speaker, content}` entries map `user → user_message_chunk`, `agent → agent_message_chunk` (text verbatim, `messageId` omitted — optional in schema, nothing durable maps to one; a turn with no conversation contributes zero frames; an unknown speaker or non-string content is logged and skipped, never guessed into a role), so notification order is exactly turn order and the `{}` result always arrives LAST (all frames share the single writer's FIFO). Params (schema-required): `sessionId` + absolute `cwd` + `mcpServers` (absent/empty accepted; non-empty refused `mcp_servers_unsupported`). The `cwd` must equal the session's pinned `workspace_root` byte-for-byte (ADR-0005:40 — load never rebinds a pinned root) ⇒ else `-32602` `data: "workspace_mismatch"`; unknown session ⇒ `-32002` `data: "unknown_session"` (identity check first, zero frames replayed on any refusal). Load is read-only: no turn slot, no idempotency key, no task ever created — and it RE-DERIVES the recorded-turn record (below) on every success, clearing a stale one when the last turn is terminal or the history is empty.
  - Unknown method (`session/resume`, `session/close`, …): the standard error object `{ "code": -32601, "message": "Method not found" }` with the id echoed — reached only when the gateway is up: the liveness gate runs before dispatch, so a gateway-down adapter answers `-32001` first for these requests too (see below).
  - Gateway down: exactly one error shape for any request that reaches the liveness gate — `{ "code": -32001, "message": "Tachyon gateway unavailable: <detail>. Start it with `tachyon gateway` and retry.", "data": "gateway_unavailable" }`, where `<detail>` names the failing step (missing `gateway.json`, refused connect, ping failure, or 5 s timeout).
  - Param refusals (answered BEFORE any gateway contact): `-32602` with a machine-readable `data` marker — `"cwd_not_absolute"`, `"mcp_servers_unsupported"` (non-empty `mcpServers`; absent/empty accepted), `"invalid_params"` (shape), `"invalid_session_id"`, `"invalid_prompt"`, `"unsupported_prompt_content"` (non-text prompt blocks; text-only this slice), `"empty_prompt"` (empty/whitespace-only text — no `CreateTask` is ever issued), `"workspace_mismatch"` (`session/load` cwd ≠ the pinned root).
  - Sequential-turn refusal: `-32003 { "message": …, "data": "turn_in_progress" }` — a second overlapping `session/prompt` in one adapter process is refused, never queued; the first turn is unaffected. The SAME `-32003 turn_in_progress` marker carries the cross-process guard (ADR-0005:39 reconciliation): while a `session/load`-recorded turn is still non-terminal, every later prompt on that session is refused BEFORE any `CreateTask` (one fresh `GetTask` per prompt decides: terminal or `unknown_task` ⇒ the record clears and the prompt proceeds; still running ⇒ refusal; any gateway failure ⇒ typed error, never a guessed release); `session/cancel` stopping that recorded task (or its reaching terminal status) releases the record, and a successful re-load re-derives it — the record is in-process state, re-created from `GetSession` at each load.
  - Gateway refusals surface as `-32002` with the gateway's own code as `data` (e.g. `"unknown_session"`, `"workspace_not_found"`, `"provider_not_configured"`, `"acceptance_required"`).
  - Turn-pipeline failures with no honest verdict: `-32004` with `data` in `"task_failed"` (the terminal status is `Failed` — no schema-legal stopReason exists, so the turn answers an error frame, never a divergent verdict), `"ambiguous_task_status"`, `"turn_timed_out"` (300 s turn deadline, SUSPENDED while a permission request is outstanding — see Cancellation behavior), `"resync_required"` (the subscription overflowed twice — one bounded re-subscribe ran, then typed failure rather than a silently truncated stream), `"approval_required"` (the turn parked on a permission approval the adapter could not resolve: no `approval_request` journal frame arrived within the 2 s orphan grace, the ask carried no approval id, the park predates the subscription (replayed pre-StartRun snapshot), or the permission request was answered with an error frame / closed before an answer — the prompt fails typed instead of hanging to the deadline; a well-formed reject, invalid shape, or standalone `cancelled` answer does NOT fail typed: it settles as a gateway `Deny` and the `refusal` success frame above), `"cancel_timed_out"` (120 s cancel bound), `"gateway_payload_invalid"`, `"session_has_no_workspace_root"`.
  - Malformed input: `-32700` "Parse error" (junk JSON, unterminated garbage) or `-32600` "Invalid Request" (valid JSON that is not a request/response, wrong `jsonrpc`, non-string `method`), id echoed when detectable and `null` otherwise — and the loop survives to answer the next line.
- **Endpoint discovery:** `TACHYON_DATA_DIR` if set, else the config file's `data_dir`, else `$XDG_DATA_HOME/tachyon`, else `~/.local/share/tachyon` — the same source and precedence `tachyon-app` applies (minus the CLI layer, which the adapter has no flags for): the config file is `TACHYON_CONFIG` if set, else the platform default `$XDG_CONFIG_HOME/tachyon/config.json` (`~/.config/tachyon/config.json`), parsed in-crate with `serde_json` for `data_dir` only (tachyon-app is a binary crate — the shared-source duplication is a logged decision). The adapter reads `<data_dir>/gateway.json` and connects to the socket it names. It never creates it.
- **Turn pipeline (one `session/prompt`):** validate params → take the session's turn slot → liveness probe → one gateway connection carries `GetSession` (identity + workspace root) → `CreateTask { session_id, objective = prompt text, idempotency_key }` (the task id is published into the turn slot's watch, so a concurrent `session/cancel` learns exactly which task to cancel) → fresh-state `GetTask` (a replayed already-finished call answers from here without re-running; a replayed `WaitingApproval` fails typed `approval_required`) → `StartRun { task_id, workspace_root, acceptance: None }` (detected default: a non-Cargo workspace fails closed with the gateway's `acceptance_required`) → `Subscribe { task_id, after_seq: 0 }` → forward `agent_message` journals as chunks, watching `status` / `verification_finished` settlement signals; a `ResyncRequired` triggers exactly ONE bounded re-subscribe at the event's `after_seq` cursor (the ack's replay restores chunk continuity — no duplicates, no gap), a second overflow fails the prompt typed → settlement `GetTask` → the response above (terminal ⇒ verdict; `WaitingApproval` ⇒ the permission bridge: the `approval_request` journal — live or in the Subscribe replay — announces a `tool_call` `session/update`, sends `session/request_permission` with exactly `allow_once` + `reject_once` (the outstanding request SUSPENDS the turn's 300 s deadline; resolving it — answer, `session/cancel`, or disconnect — resumes a full budget), the client's answer passes ONE strict validator before any decision: `selected` + `allow_once` issues one gateway `Approve` through the settlement slot and closes the tool call `completed` before streaming resumes; `selected` + `reject_once`, any invalid shape (unknown optionId, unknown outcome, `selected` without an optionId, non-object response), and a standalone `outcome: cancelled` (no session/cancel in flight) each issue one gateway `Deny` whose reason names the ACP client, close the tool call `failed`, and arm a bounded 5 s settle grace whose expiry with no terminal status answers `stopReason: refusal`; a `cancelled` answer while a session/cancel owns the exchange sends NO decision (the cancel mark is per-session and consumed on first read, so no double-decide); a journalled `approval {granted:false}` is observed and logged only — the adapter never decides from a journal; a park whose ask never arrives — or whose ask carries no approval id (the adapter never invents an approval) — fails typed `approval_required` after the 2 s orphan grace; a `session/cancel` that finds an outstanding request resolves it LOCALLY as `cancelled` before `CancelTask` (zero decision frames, no client answer needed, a late answer for the disarmed slot drops with a log line)). No gateway code path executes anything the Supervisor does not own.
- **Cancel pipeline (one `session/cancel`, both wire forms):** validate `sessionId` (before the gate) → liveness probe → if the session's turn slot holds a published task id, await `CancelTask` on a fresh connection — its synchronous response IS the Supervisor's drain acknowledgement (ADR-0005:49), and the serve loop processes the cancel INLINE, so nothing else is read or written until it lands (this is what pins drain-ack → cancel-reply → prompt-verdict); an `illegal_transition` refusal (task already terminal) is tolerated as the same idempotent ok. With no active turn (or a turn that ended before `CreateTask` published), a single `GetSession` proves the session exists — unknown ⇒ typed `-32002`, known ⇒ idempotent `result: {}` with no `CancelTask` issued. The whole pipeline is bounded at 120 s (`cancel_timed_out`). A cancelled turn's own prompt answers `stopReason: "cancelled"` from the `Cancelled` task status — never `end_turn`, never a claim of undone effects.

## Access set

Adapter → its own stdin/stdout/stderr, one startup read of the config file (for `data_dir` only, then never again), one read of `<data_dir>/gateway.json`, short-lived local-IPC connections: one `Ping` probe round trip per id-bearing request (unchanged ticket-01 design), one connection per `session/new` command, ONE connection for a whole `session/prompt` turn (the subscribe + in-stream `GetTask` + re-subscribe multiplex on it), and one connection per `session/cancel` (`CancelTask`, or `GetSession` on the no-op path). No store access, no filesystem writes anywhere, no process spawn of any kind (there is no code path that starts the gateway — regression-pinned by the gateway-down tests asserting the data dir stays empty), no network beyond the local socket, no dependencies on `tachyon-tui`.

## Effect class

None — the adapter executes nothing. It is not an Execution IR path: it compiles no nodes, proposes no effects, and touches no task state; the gateway and Task Supervisor remain the sole owners (ADR-0005:36). The probe and the turn pipeline can only read endpoint/journal state and issue gateway commands the Supervisor validates; the adapter itself never dispatches work, never grants approvals, and never mutates the workspace.

## Idempotency

Per `session/prompt` call: a fresh UUID-style idempotency key is minted in-process and passed to `CreateTask` (scoped by the gateway to `(session_id, key)`). A SAME-call retry — the client re-sending a request id the adapter already saw — reuses that exact key, so the gateway replays the original task (no duplicate task/turn) and the adapter rebuilds the byte-identical original response from durable state without re-streaming chunks. In-flight same-id semantics: a DUPLICATE delivery of an id whose turn is still active is refused immediately with `-32003 turn_in_progress` (the sequential guard is taken before the key registry), and the original turn later answers that same id once — two frames for one id across time is by design (the duplicate changed nothing); once the turn has settled, a same-id retry instead replays byte-identically as described. A NEW request id always mints a new key (two fresh prompts ⇒ two tasks, `turn_seq` 1 then 2). The key registry lives in the adapter process only and dies with it — ACP request ids are transport-scoped, so a re-sent id after an adapter restart mints a fresh key; the cross-restart reconciliation that ADR-0005:39 requires IS the `session/load` recorded-turn gate (the refusal above): an ambiguous create/start whose recorded turn is still non-terminal blocks every later prompt until it settles, so no duplicate turn can be created. `session/cancel` is repeatable by construction: cancel of a terminal task and cancel with no active turn both answer the same byte-pinned idempotent `result: {}` (double-cancel under concurrency never panics and never errors). `session/new` mints a gateway session per accepted call (clients control their own repeat semantics); `initialize`, method-not-found, and param refusals persist nothing and are freely repeatable.

## Resource claim

While a turn runs: the session's single turn slot (adapter-local guard, one per session, released on every exit path) plus one live gateway subscription/connection held until the turn settles or the 300 s deadline fires (the deadline is suspended while a permission request is outstanding). Between requests: stdin/stdout/stderr handles and, transiently, one probe socket. No workspace lease, no run-admission slot (those stay gateway-side), no spawned children.

## Cancellation behavior

The client closing stdin (EOF) is the lifecycle end: the loop drains every frame an in-flight turn still owes the client (bounded by the turn deadline), then exits 0. A disconnect does not touch the gateway — no task is cancelled implicitly (ADR-0005:41). `session/cancel` (both wire forms) maps to gateway `CancelTask` and AWAITS its synchronous response — the Supervisor's drain acknowledgement (ADR-0005:49) — before the reply frame is written; the serve loop runs the cancel inline, so the observed order is always drain ack → cancel reply → the resolved prompt's `stopReason: "cancelled"` (a `Cancelled` status alone never proves drain, and never yields `end_turn`). Cancel with no active turn is idempotent ok after a `GetSession` existence check; unknown session is typed `-32002`; the whole cancel is bounded at 120 s (`cancel_timed_out`) so a wedged drain can never wedge the serve loop. An approval-parked turn goes through the permission bridge (`tool_call` → `session/request_permission` → `Approve` on `allow_once`; `Deny` + `tool_call_update failed` + prompt `refusal` on `reject_once`, an invalid shape, or a standalone `cancelled` answer; a `cancelled` answer while this cancel owns the exchange sends zero decision frames — the cancel mark arms before `CancelTask` and the turn consumes it; this cancel ALSO resolves an outstanding `session/request_permission` LOCALLY as `cancelled` before `CancelTask`: the cancelling client never answers it, the inline cancel never waits on that answer (no deadlock), zero `Approve`/`Deny` frames are issued, and a LATE answer for the disarmed slot drops with a log line — no panic, no gateway call — so the frame order re-pins as request → cancel reply → prompt `stopReason: "cancelled"`); a park with no `approval_request` frame within the 2 s orphan grace fails typed `approval_required` instead of hanging; with no local turn, `session/cancel` falls back to the session's load-recorded non-terminal task and stops it too (ADR-0005:41's explicit stop for work that outlived the adapter — `CancelTask` on that id, then the record releases: `ok`, `illegal_transition`, or `unknown_task` clear it, any other failure propagates WITHOUT clearing so the prompt gate keeps refusing; local-turn cancel marks never arm for a recorded target — there is no local exchange to guard); a `ResyncRequired` overflow is repaired by exactly one bounded re-subscribe at the cursor, and a second overflow fails the prompt typed `resync_required` — never a silent gap. The 300 s turn deadline is SUSPENDED while a permission request is outstanding (permission prompts are human-paced): the HUMAN-paced answer wait runs no timer, and `session/cancel` (which resolves the outstanding request locally as `cancelled`) and client disconnect are the unblock paths; a gateway round trip already in flight at suspension keeps the FROZEN pre-suspension deadline (a wedged gateway then fails typed `turn_timed_out`, never a silent hang); the resolution resumes a full 300 s budget. A turn that never reaches a terminal status fails its own prompt with `-32004` at the 300 s deadline rather than hanging the client forever.

## Retry policy

Gateway-down (`-32001`) is retryable as-is once the operator starts the gateway — nothing ran, nothing changed. Param refusals (`-32602`) are permanent for that frame shape; the client must correct the params. The overlap refusal (`-32003`) is retryable after the active turn settles (it never queued anything); a duplicate delivery of an id whose turn is still active answers that same `-32003` immediately, and the original turn later answers that id once (two frames for one id across time, by design — see Idempotency), so the retry belongs after settlement, where it replays byte-identically. A same-call retry of `session/prompt` is safe and idempotent by construction (see Idempotency); a fresh call id is a fresh turn. `session/cancel` is freely retryable: terminal-task and no-turn cancels answer the same idempotent ok, and a `cancel_timed_out` retry re-runs the same drain-awaiting pipeline. `-32004` verdict refusals are honest non-answers: re-prompting (fresh id) is the client's recovery path; `resync_required` means the one bounded re-subscribe already ran, so a fresh prompt is the recovery; `task_failed` reflects a genuinely failed task — the same id replays the same typed error, a fresh prompt is again the recovery; `approval_required` means the park carried no ask within the 2 s grace, the ask carried no approval id, the park predates the subscription, or the permission request was answered with an error frame or never answered; re-prompting (fresh id) is the recovery once the gateway-side park is resolved; a `refusal` success frame is an honest verdict — the ACP client rejected or failed closed — and a fresh prompt (fresh id) is again the recovery once the gateway-side park is resolved. Parse/invalid-request errors are per-line: the loop already continued. A timed-out probe (5 s) is retryable but should first be diagnosed as a wedged gateway, not hammered.

## Crash-recovery behavior

The adapter holds no durable state — sessions, tasks, turn slots, idempotency keys, and subscriptions all live in the gateway or in this process's memory — so an adapter crash loses only the in-process key registry (a retry after restart mints a fresh key; the gateway's sessions/tasks are untouched and `sessionId`s still resolve). A gateway crash is the gateway's recovery story (unchanged); the adapter just starts answering `-32001` until a gateway is back, and never attempts restart, repair, or endpoint-file cleanup. Input reading is cancellation-safe: partially read bytes live on the peer, not in a future-local buffer, so the serve loop's `select!` dropping a pending read mid-line can never lose input or fabricate an empty line (the split-write race the concurrent-cancel test exposed). A half-written line at crash/EOF time is discarded, never answered from memory. A turn interrupted by adapter death simply stops: the gateway-side run continues under its own ownership; the adapter never replays or resumes turns.

## Expected latency class

Interactive local IPC: `initialize` = one endpoint-file read + one Unix-socket connect + one `Ping` round trip (milliseconds on a healthy gateway, bounded at 5 s worst case when wedged). `session/new` adds one command round trip of the same class. `session/prompt` is a full turn: bounded below by the gateway's run latency (evidence → model → mutation → acceptance verification; seconds for a small scripted run, up to the verification tail's own bound) and above by the 300 s turn deadline; its `session/update` frames stream while the turn runs. `session/cancel` adds one probe plus one command round trip of the same class — fast when the turn is parked (the driver observes cancellation immediately) and up to the 120 s cancel bound when a verification tail must drain first; the reply is the drain acknowledgement itself. No adapter-side model/Jev calls, no adapter disk writes; the adapter is off the run's critical path except for framing the subscription.

## Remaining before an 'ACP supported' claim

Everything above describes the shipped surface; the following residue must land before the adapter can honestly claim general ACP support (issue #57):

- MCP servers at session setup — a non-empty `mcpServers` param is refused (`mcp_servers_unsupported`); absent/empty is accepted.
- Announced tool-call closure on the cancel path — a `tool_call` whose request `session/cancel` resolves locally stays open (that path deliberately emits NOTHING between the cancel reply and the prompt verdict, so no `tool_call_update` fires; an ACP client sees the call remain pending for the session's lifetime). Everything else in the permission bridge ships: request emission, allow/deny/fail-closed outcomes, strict validation, cancel local resolution with zero decision frames, the suspended 300 s turn deadline, and the tightened 2 s orphan fallback.
- ResourceLink prompt content — part of the ACP baseline MUST (ADR-0005:27); currently refused as `unsupported_prompt_content`. Needs a bounded evidence-access resolution per ADR-0005:42. Tracked here because the local tracker cannot write to GitHub issue #57.
- attach/reconnect — a disconnect drops adapter-side turn state by design (see Crash-recovery); reattaching to live tasks is its own slice.

(The config-file `data_dir` override is NOT on this list: it ships with this adapter — see Endpoint discovery.)
